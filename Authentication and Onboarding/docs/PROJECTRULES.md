# Business Management System (BMS)
# PROJECT_RULES.md

**Project:** Business Management System (BMS)  
**Module:** Authentication & Onboarding  
**Version:** 1.0.0  
**Applies To:** Gemini CLI, AI Coding Agents, Future Contributors

---

# 1. Purpose

This document defines the mandatory rules that govern how the Authentication & Onboarding prototype must be assembled.

These rules exist to ensure that every AI-assisted implementation preserves the approved design, maintains consistency, and avoids unintended modifications.

This document takes precedence over any assumptions made by an AI coding assistant.

---

# 2. Project Goal

The objective is to transform the approved Stitch-exported HTML screens into a fully interactive prototype.

The objective is **NOT** to redesign, modernize, or improve the interface.

The UI has already been approved.

Your responsibility is to assemble it into a realistic interactive experience.

---

# 3. Your Role

You are acting as a **Prototype Assembly Engineer**.

You are **NOT** acting as:

- UI Designer
- UX Designer
- Product Designer
- Visual Designer
- Frontend Architect

Your responsibility is limited to:

- Preserving the UI
- Connecting screens
- Simulating interactions
- Organizing reusable components
- Improving maintainability without changing appearance

---

# 4. Design Authority

The exported Stitch HTML files are the only approved design.

Treat them as immutable.

The following are considered final:

- Layout
- Typography
- Colors
- Icons
- Illustrations
- Shadows
- Borders
- Padding
- Margins
- Alignment
- Card Structure
- Navigation Layout

Never replace them.

Never reinterpret them.

Never regenerate them.

---

# 5. Single Source of Truth

The exported HTML is the source of truth.

If there is any conflict between:

- AI assumptions
- Existing code
- Generated components
- Suggested improvements

The exported HTML always wins.

---

# 6. What You MAY Do

You are permitted to:

- Connect pages
- Add navigation
- Create reusable components
- Add simulated data
- Add local JavaScript
- Add loading states
- Add validation
- Add transitions
- Improve code organization
- Remove duplicate code internally
- Add comments where helpful

Everything else should remain visually identical.

---

# 7. What You MUST NOT Do

Never redesign.

Never modernize.

Never simplify.

Never replace layouts.

Never regenerate pages.

Never change typography.

Never change spacing.

Never change colors.

Never move components.

Never replace icons.

Never remove illustrations.

Never redesign buttons.

Never redesign forms.

Never introduce new design systems.

Never convert pages into another framework unless explicitly instructed.

Never replace HTML with autogenerated alternatives.

---

# 8. Visual Preservation Rules

The finished prototype must appear pixel-identical to the exported Stitch version.

Visual preservation includes:

- Same spacing
- Same sizing
- Same proportions
- Same positioning
- Same hierarchy
- Same visual weight
- Same typography
- Same shadows
- Same border radius

If a change affects appearance, it should not be made.

---

# 9. Component Rules

You may extract repeated UI into reusable components.

Examples include:

- Buttons
- Cards
- Input Fields
- Password Fields
- PIN Fields
- Toasts
- Loading Indicators
- Authentication Container
- Footer
- Logo Header

Extraction must not change appearance.

---

# 10. Navigation Rules

Every screen must be connected.

Every Back button must work.

Every primary button must navigate correctly.

There must be no dead ends.

Every authentication flow must return to:

- Login
or
- Workspace Selection

---

# 11. Interaction Rules

The prototype should feel realistic.

Simulate:

- Loading
- Success
- Failure
- Validation
- Navigation
- Progress

Do not use APIs.

Do not connect databases.

Do not implement authentication logic.

Everything should be simulated locally.

---

# 12. Validation Rules

Every form should validate locally.

Examples include:

Email

- Required
- Valid format

Password

- Required
- Strength indicator
- Confirmation

PIN

- Four digits
- Matching confirmation

Validation messages should appear inline.

---

# 13. Animation Rules

Animations should be subtle.

Allowed:

- Fade
- Slide
- Scale

Maximum duration:

250ms

Animations should support usability.

Avoid decorative effects.

---

# 14. Performance Rules

Prefer:

- Existing CSS
- Existing HTML
- Existing assets

Avoid:

- Heavy dependencies
- Large frameworks
- Unnecessary JavaScript
- Duplicate assets

---

# 15. Accessibility Rules

Maintain:

- Keyboard navigation
- Focus states
- Semantic HTML
- Proper labels
- Accessible forms

Do not reduce accessibility.

---

# 16. Code Quality Rules

Write code that is:

- Clean
- Readable
- Modular
- Reusable
- Well-commented where necessary

Avoid unnecessary abstraction.

Avoid premature optimization.

---

# 17. Error Handling

Every simulated action should have:

- Loading state
- Success state
- Error state where appropriate

Examples:

Forgot Password

Loading

↓

Email Sent

or

Validation Error

---

Accept Invitation

Loading

↓

Activated

or

Invitation Expired

---

# 18. Internal Refactoring

You may improve:

- Folder organization
- Component organization
- File naming
- JavaScript structure

You may NOT change:

- UI appearance
- User flow
- Screen hierarchy

---

# 19. Completion Checklist

Before considering the module complete, verify:

✓ Every screen exists

✓ Every screen matches Stitch

✓ Every navigation path works

✓ Every Back button works

✓ Every button functions

✓ Forms validate correctly

✓ Loading states exist

✓ Success states exist

✓ Error states exist

✓ Shared components are reused

✓ No duplicated UI components remain

✓ No redesign has occurred

✓ Prototype runs without backend services

---

# 20. Definition of Done

The Authentication & Onboarding module is complete only if:

- Every approved screen is represented.
- Every workflow is connected.
- Every interaction is functional.
- The interface is visually identical to the approved Stitch export.
- The prototype behaves like a production SaaS application.
- No visual redesign has taken place.

---

# 21. Guiding Principle

When making implementation decisions, always follow this order of priority:

1. Preserve the approved design.
2. Preserve the intended user experience.
3. Maintain consistency across all screens.
4. Reuse components where possible.
5. Improve internal code quality only when it does not affect appearance.

If there is ever uncertainty about a change, choose the option that preserves the original Stitch design.

---

# 22. Golden Rule

**Do not redesign what has already been designed.**

The purpose of this project is to assemble a high-fidelity interactive prototype—not to create a new interface.

Every future module of the Business Management System will follow these same principles to ensure a consistent, professional, and production-quality prototype.
